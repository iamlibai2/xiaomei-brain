# 延后事项台账

> 更新时间：2026-07-28  
> 本文只记录已经讨论过、明确留到后续的设计，不代表当前迭代承诺。
> 实施前仍需结合当时的代码和产品目标重新确认，不机械照搬旧方案。

## 1. Agent 状态的真实性

当前 Desktop 已能展示关系、情绪、精力、身体感受、欲望、激素、矛盾和行为倾向，
但状态系统仍需进一步收束为一份真实、统一的数据源：

- 去掉 `control`、`novelty`、`integrity`、`aesthetics` 等实验性固定值；
- 明确每个状态的来源、持久化方式、更新条件和衰减规则；
- 排查长期处于 0% 或 100% 的状态是否符合设计；
- 保证对话上下文、Desktop、梦境和自主行为读取的是同一份状态；
- 状态界面成熟后再决定保留多少原始数值，避免长期停留在调试面板形态。

## 2. 自主行为的隔离执行

继续排查仍在 Living 主线程同步执行、可能阻塞实时对话的自主行为，例如：

- 学习；
- `work`；
- `alarm`；
- Goal/PACE 推进；
- 元技能学习；
- 主动表达、关心和需要 LLM 生成内容的行为；
- 其他由 `ActionDispatcher` 触发的耗时行为。

方向已经明确：

- 复用现有 `Agent` 类，不另写一套 Agent；
- 每次行为创建隔离的临时 Core/运行现场；
- 对话与自主行为不共享可变的 session、turn、取消状态和临时消息；
- 每个 Agent 第一版只并行一个自主行为；
- 停止、失败和恢复有明确的 checkpoint 语义；
- 身份、记忆、Goal、Drive 和数据库仍属于同一个 Agent。

梦境是例外：梦境期间允许消息进入队列，但不接受实时打断；Desktop 明确展示“梦境中”
以及“消息将在醒来后处理”。

## 3. Goal、PACE 与 Assignment 的关系

当前 Assignment 是外部工作约定，Goal 是 Agent 自己的内部目标，两者保持独立。
后续需要重新讨论：

- Assignment 是否以及如何影响 Goal/Purpose；
- PACE 与 Assignment checkpoint 是否共享机制；
- Desktop 中更丰富的 Goal、PACE 阶段、下一步和受阻原因；
- 未通过验收后的自动返工；
- 是否使用独立验收模型。

当前不自动返工，不把 Assignment 强行挂接到 Goal，也不批量转换历史 Goal。

## 4. 多 Agent 协作

当前阶段只要求多个 Agent 像多个独立员工一样分别聊天、分别接受委托。
以下能力等单个 Agent 足够成熟后再设计：

- Agent 之间互相委托；
- 工作拆分、交接和结果汇总；
- 多 Agent 协作过程的可观察性；
- 冲突、失败、权限和责任边界；
- 企业内法务、财务、人事、文档和编码 Agent 的协作方式。

不预设中央 Gateway 或中央管理者。未来方案必须继续遵守“一 Agent 一世界”和
“先有 Agent，Gateway 只是它与外界交互的接口”。

## 5. 人物身份与权限

人物身份第一版已经建立，飞书和钉钉绑定也已实现。后续仍包括：

- 人脸绑定；
- 声纹绑定；
- 新设备与身份恢复；
- 企业身份登录、组织架构和岗位权限；
- 本机管理权限、对话授权和敏感操作授权的统一模型；
- 现有数据库中 `user_id` 的语义拆分与渐进迁移；
- 旧 `contacts/identities.yaml` 身份实现的最终清理。

现阶段不批量重命名已有数据库列，不牺牲其他开发机上的历史 Agent 数据。
`person_id` 是新人物领域的名称，旧表迁移必须使用增量升级脚本。

## 6. 对话式管理与分析模式

长期方向是尽可能通过人与 Agent 对话完成配置和管理，而不是把产品变成设置面板：

- 通过对话设置名字、职责、性格和工作方式；
- 通过对话配置 Channel、Binding 和 Person 绑定；
- 通过结构化 Clarify/Action 完成确认和高风险操作授权；
- 设计类似《西部世界》Host 分析模式的深层观察与管理入口；
- 普通对话界面不暴露原始思维链。

现有 Admin HTTP REST 暂不扩展，后续确认无消费者后再删除；管理领域逻辑不能依赖
HTTP 路由。CLI 继续承担宿主机上的底层运维入口。

## 7. Gateway 与其他交互端

已经讨论但暂未优先实施：

- `connect.capabilities` 能力协商；
- TUI 基于当前公开协议重新实现；
- CLI、TUI、Desktop 和 Channel 对 Clarify、Action、附件、Artifact、Assignment
  的完整体验一致性；
- 清理旧协议文档与已不再需要的兼容描述。

Desktop 和仓库内客户端目前同步开发，没有为旧客户端保留双字段兼容的必要。

## 8. Channel 扩展

- 个人微信/微信群接入：受平台能力限制，暂不作为核心链路；
- 企业身份和更多企业 Channel：等真实企业场景出现后再做；
- 飞书、钉钉更复杂的群聊策略：继续保持固定、开箱即用的策略，除非真实使用证明需要配置。

## 9. Desktop 信息架构

- “上下文”栏目目前保留；待状态、记忆和活动信息迁移稳定后，再决定是否关闭；
- 右侧栏后续可增加 Goal/PACE 的真实详情，但不做项目管理看板；
- 状态页当前承担展示 Agent 差异性的作用，成熟后再做信息收敛；
- 不增加会话归档、分类等要求用户维护信息的功能。

## 10. 发布工程

不影响核心能力的发布事项放到后面集中处理：

- 正式自动更新服务、版本清单、升级失败回退；
- Windows 安装包签名；
- macOS/Linux 安装与分发；
- 进一步优化 MSI 构建压缩耗时。

Runtime 单归档分发已经完成，不属于待办。

## 11. 明确不做或已经否决

以下内容不要作为“遗留功能”重新提出：

- 会话归档与复杂分类；
- 中央 Agent 管理服务；
- 远程管理其他人的 Agent；
- 把 Assignment、Goal、Dream 合并成同一种对象；
- 第二套 Agent Core 实现；
- 通用工作流编排器；
- 默认展示原始思维链；
- 第一阶段多个 Assignment 并行；
- 为旧 Desktop 保留 V2/V3 双字段兼容；
- 记忆详情跳转到来源会话。
