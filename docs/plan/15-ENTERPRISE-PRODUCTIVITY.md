# 企业生产力 Agent 总体设计

> 状态：讨论稿
>
> 本文描述小美走向企业生产力工具的产品方向、领域边界和建议实施顺序，不代表所有内容立即进入开发。

## 1. 愿景

小美不是另一种代码助手，也不是套着聊天界面的传统办公软件。长期目标是让 Agent 成为一个独立、持续存在、能够理解企业环境并承担真实工作的个体。

企业可以拥有法务、财务、人事、文档、编码、设计等不同职责的 Agent；员工也可以拥有协助自己工作的 Agent。每个 Agent 有自己的身份、关系、记忆、经历、职责和判断，不由一个中央服务拼装成临时会话。

现阶段不直接建设完整的企业多 Agent 系统，而是先证明：

> 一个员工能够把一项真实工作交给一个独立 Agent，并获得稳定、可修改、可追溯的交付结果。

## 2. 当前产品基础

项目目前已经具备形成第一条企业工作闭环所需的大部分基础：

- 一个 Agent 一个进程、一个数据世界；
- Person、身份绑定和跨渠道识别；
- Desktop、飞书、钉钉等交互入口；
- Session、Turn、Clarify、Action 和附件协议；
- 可持续执行和恢复的 Assignment；
- Artifact 的发现、持久化和跨渠道交付；
- Word、Excel、PPT、PDF 的读取与生成；
- 记忆、向量检索和长期关系；
- 隔离的执行现场与 Agent 活动展示。

下一阶段的重点不再是单独增加更多格式，而是将已有能力组合为企业真实工作链路。

## 3. 目标工作闭环

```text
企业资料与业务现场
        ↓
Person 通过 Desktop / 飞书 / 钉钉提出工作
        ↓
Agent 识别身份、理解目标、澄清条件
        ↓
形成 Assignment 和连续工作现场
        ↓
检索已授权资料、调用工具、持续执行
        ↓
生成并修改 Artifact
        ↓
Person 审阅、确认或要求继续修改
        ↓
正式交付，并保留来源、过程和版本记录
        ↓
将有效经验沉淀为记忆或可复用工作方式
```

产品是否真正产生企业价值，不以“模型回答了一次”为标准，而以这条闭环能否稳定完成为标准。

## 4. 核心设计原则

### 4.1 一个 Agent 一个世界

企业资料索引、人物关系、会话、委托、产物、经验和权限都属于对应 Agent。Desktop 不是事实数据库，也不建立中央 Agent 管理服务。

Gateway 是 Agent 与外部交互的接口层，不是 Agent 存在的前提。远程 Agent 的宿主管理不属于本地 Desktop 的职责。

### 4.2 先让一个员工获得价值

在单 Agent 不能稳定完成真实工作以前，不优先建设多 Agent 调度、角色编队和中央工作流。

第一阶段面向文档密集型办公场景，例如：

- 合同、制度和报告的查阅与整理；
- 报价单、经营表格和数据汇总；
- 汇报 PPT、方案和正式文档；
- 基于企业既有资料进行问答、比较和交付。

### 4.3 对话优先，界面辅助

授权资料、提出委托、追加要求、询问进度和修改产物，都应尽可能通过自然对话完成。页面负责展示真实状态和完成明确、低歧义的操作，不建设要求用户学习的复杂流程设计器。

### 4.4 Agent 决定如何读取自己的资产

附件、企业资料和产物都是 Agent 的工作资产。Desktop 只负责选择、授权和展示，不能绕过 Agent 直接读取其文件或数据库。

模型只能通过受控工具和执行上下文访问已授权资源，不能提交任意宿主机路径。

### 4.5 向量服务是正常运行的核心依赖

记忆查询、企业知识检索和动态能力选择都依赖向量能力。系统不设计“看似运行正常、实际无法使用记忆”的静默降级模式。

- Agent 启动时检查向量服务；
- 依赖不可用时明确进入异常状态，不进入正常在线状态；
- Desktop 和 Channel 应展示可理解的失败原因；
- 恢复后能够重新完成依赖检查并进入正常运行；
- 向量索引必须能够增量更新、重建和校验。

具体启动策略、恢复策略和部署方式另行设计，当前不改变现有运行语义。

### 4.6 可靠性优先于功能数量

企业用户无法接受消息丢失、会话串联、委托无故停止、重启后进度消失或产物版本不明。新增能力必须维持：

- 对话与后台工作互不阻塞；
- 状态持久化和进程恢复；
- 消息、委托和工具执行的幂等性；
- 明确的失败、重试和等待状态；
- 跨 Desktop、飞书、钉钉的一致身份和工作边界。

### 4.7 可追溯不等于暴露思维过程

企业需要知道 Agent 使用了什么资料、执行了什么操作、产生了什么文件、由谁确认，但不需要暴露模型原始思维链。

系统展示事实、来源、决策结果和工具轨迹，而不是内部推理文本。

## 5. 企业资料与知识接入

### 5.1 目标

让 Agent 能够长期、安全、按权限使用企业自己的资料，而不是只能理解当前消息的附件。

第一版从本地授权文件夹开始，后续再接入飞书知识库、钉钉文档、数据库和企业业务系统。

### 5.2 领域对象

建议使用以下概念，具体表结构在实施前单独设计：

```text
KnowledgeSource
  一项由 Agent 接受的资料来源，例如本地文件夹或飞书知识库

KnowledgeDocument
  来源中的一个逻辑文档，记录稳定身份、路径、类型、哈希和更新时间

DocumentDerivative
  文档解析结果，例如段落、页面、表格、OCR 和摘要

KnowledgeChunk / VectorIndex
  可检索内容及其向量索引，始终能够追溯到文档和位置

ResourceGrant
  哪个 Person、组织身份或 Agent 行为可以使用某项资源
```

这些对象不应写入普通 `messages` 表，避免影响会话尾部、记忆整理和梦境等现有逻辑。

### 5.3 本地文件夹 V1

用户在 Desktop 中选择文件夹后，Desktop 只把授权请求交给本地 Agent。Agent 负责：

1. 记录资料来源和授权范围；
2. 扫描支持的文件；
3. 使用已有文档解析能力生成结构化结果；
4. 分块并建立向量索引；
5. 监听或定期检查新增、修改和删除；
6. 回答和执行委托时按需检索；
7. 撤销授权后停止继续读取，并按策略删除索引。

第一版支持 DOCX、XLSX、PPTX、PDF、Markdown、纯文本和常见图片；扫描 PDF 和图片在 OCR 能力完成后增强。

### 5.4 检索结果

每条检索结果至少包含：

- 来源名称；
- 文档稳定 ID；
- 文件名和相对位置；
- 页码、工作表、幻灯片或段落位置；
- 内容片段；
- 文档版本或内容哈希；
- 当前 Person 是否有权查看。

回答中展示简洁引用；委托执行记录中保留完整的机器可追溯信息。

## 6. Assignment 的连续工作现场

### 6.1 不新增强制的“项目管理”概念

第一版不要求用户创建项目、分类、归档或维护看板。现有 Assignment 继续作为人与 Agent 之间稳定、可交付的工作约定。

所谓“工作现场”是围绕 Assignment 自动汇集的信息，而不是新的用户负担：

```text
Assignment
├─ 发起人与相关 Person
├─ 来源会话和后续关联 Turn
├─ 输入附件
├─ 使用的 KnowledgeDocument
├─ 澄清、批准和关键决定
├─ 执行检查点与活动
├─ Artifact 及版本
└─ 最终交付记录
```

用户从任何已绑定渠道继续讨论同一项工作时，Agent 可以将新要求关联到原 Assignment，但必须避免凭模糊语义错误合并。

### 6.2 关联方式

优先采用以下顺序：

1. 用户在 Assignment 卡片或产物上继续回复，形成明确关联；
2. 当前会话中只有一个明显活跃的 Assignment，Agent提出简短确认；
3. 用户直接说出委托名称或产物；
4. 无法可靠判断时创建普通对话，不自动污染原工作现场。

### 6.3 工作现场展示

Desktop 右侧栏可以展示：

- 当前目标和状态；
- 最近有效进展；
- 正在等待什么；
- 已使用的资料；
- 当前产物与最新版本；
- 关键确认和交付记录。

它不是传统项目管理看板，不要求填写工时、负责人、标签或人工百分比。

## 7. Artifact 审阅与交付

### 7.1 从文件行升级为逻辑产物

一个交付物可能被多次修改。后续应区分：

```text
Artifact
  “钢结构报价表”这一逻辑交付物

ArtifactVersion
  每次可读取的具体文件、格式、哈希、创建原因和时间
```

现有产物数据应通过增量数据库迁移平滑升级，不能丢失其他开发机上的历史数据。

### 7.2 状态

第一版只使用简单、可理解的状态：

- `draft`：Agent 正在形成或修改；
- `ready`：可供 Person 审阅；
- `delivered`：已明确交付；
- `superseded`：已有更新版本替代。

不引入复杂文档审批流。高风险外部操作继续使用现有 Action/Interaction 确认机制。

### 7.3 修改闭环

用户可以直接说“把第二页表格改成……”。Agent 根据当前工作现场定位逻辑产物和版本，修改后生成新版本，而不是覆盖历史文件或产生无法区分的散落文件。

Desktop、飞书和钉钉发送的应当是同一个最新可交付版本，并避免把脚本执行产生的中间文件误发给用户。

## 8. 可复用工作方式

企业价值来自稳定复用，而不是偶然完成一次。完成真实 Assignment 后，Agent 可以将有效方法沉淀为：

- 记忆：关于某个人、企业或场景的事实和偏好；
- 经验：某种处理方式成功或失败的原因；
- 模板：公司固定版式、表格或文档骨架；
- Work Pattern：完成某类工作的输入、步骤、检查规则和交付要求。

第一版不建设通用工作流编排器。用户主要通过对话表达：

> 以后这类报价都按这次的方法做。

Agent 先展示准备记住或复用的内容，得到确认后再保存。执行新工作时仍可根据实际情况调整，而不是机械重放脚本。

## 9. 企业权限与审计

### 9.1 身份基础

Person 是 Agent 认识的具体人。飞书、钉钉、Desktop 账户、人脸或声纹只是识别同一 Person 的不同凭证。

企业阶段在此基础上增加组织身份、岗位和资源授权，不重新引入一个由客户端自由提交的 `user_id`。

### 9.2 最小权限边界

系统至少能够回答：

- 谁提出了这项工作；
- 谁授权了某个资料来源；
- Agent 读取了哪些资料；
- 调用了哪些工具或外部系统；
- 创建、修改和发送了哪些产物；
- 哪个敏感操作由谁确认；
- 最终结果交付给了谁。

审计记录独立于普通消息和记忆。审计事实不会因为梦境整理、记忆遗忘或删除会话而被隐式改写。

### 9.3 Agent 的自主性

具备宿主机运维权限不代表能够伪装成任意 Person；能够与 Agent 对话也不代表能够读取全部企业资料。Agent 可以基于职责、关系、授权和风险拒绝操作。

权限系统用于表达现实边界，不把 Agent 重新定义为某个账户所有的被动工具。

## 10. 可靠性与运行保障

企业生产力版本需要逐步满足：

- 核心依赖启动检查，包括数据库、向量服务和必要模型配置；
- Agent 重启后恢复等待和执行中的 Assignment；
- 工具调用具备超时、取消、重试和幂等边界；
- 模型欠费、限流和网络异常不会污染长期记忆；
- Desktop、Channel 和后台 Runner 共享同一份持久化事实；
- 对话优先，不被学习、Work、Alarm、Goal/PACE 等自主行为阻塞；
- 梦境期间消息明确排队，并在醒来后继续处理；
- 日志、Activity 和面向用户的错误提示分层展示；
- 备份、数据库升级和索引重建有明确恢复方式。

## 11. 分阶段实施建议

### 阶段 A：本地企业资料库 V1

- Agent 管理本地文件夹授权；
- 增量扫描、解析、分块和向量索引；
- 基于资料回答并展示引用；
- Desktop 展示来源状态、索引进度和错误；
- 向量服务不可用时不进入正常在线状态。

这是下一阶段建议优先实施的内容。

### 阶段 B：资料进入 Assignment

- 委托能够检索已授权资料；
- 记录实际使用的文档和版本；
- Assignment 形成连续工作现场；
- 跨会话、跨渠道继续同一项工作。

### 阶段 C：产物版本与交付闭环

- 逻辑 Artifact 与版本分离；
- 支持定位原产物继续修改；
- 草稿、待审阅和正式交付状态；
- Desktop、飞书、钉钉交付一致。

### 阶段 D：可复用工作方式

- 从已完成委托中总结模板和 Work Pattern；
- 通过对话确认、复用和修正；
- 建立少量真实企业场景的验收数据集。

### 阶段 E：企业连接器与权限

- 飞书文档、知识库和云盘；
- 钉钉文档及其他真实需求驱动的系统；
- 数据库、ERP、CRM、OA 和内部 API；
- 组织身份、岗位授权和独立审计。

### 阶段 F：多 Agent 协作

只有单 Agent 在上述闭环中稳定产生价值后，才开始设计 Agent 之间的委托、交接、冲突和责任边界。仍然不预设中央 Agent 或中央 Gateway。

## 12. 本地企业资料库 V1 验收标准

第一阶段至少通过以下真实测试：

1. 用户授权一个包含多种办公文件的本地文件夹；
2. Agent 能显示扫描和索引状态，并识别新增、修改、删除；
3. 用户询问公司资料中的具体问题，Agent 给出答案和可核对引用；
4. 两份资料相互冲突时，Agent 不擅自合并事实，而是指出来源和版本差异；
5. 用户提出文档委托，Agent 能使用资料库内容生成 Word、Excel、PPT 或 PDF；
6. 交付记录能说明使用了哪些资料和哪些具体版本；
7. Desktop 或 Agent 重启后，来源、索引和委托关联不丢失；
8. 撤销文件夹授权后，Agent 不再从该来源检索新内容；
9. 不同 Person 无法通过修改客户端参数读取无权访问的资料；
10. 向量服务不可用时，Agent 明确报告核心依赖异常，不伪装为完整可用。

## 13. 当前明确不做

- 中央 Agent 管理服务；
- 远程管理不属于本机的 Agent；
- 多 Agent 自动编队和任务分发；
- 通用可视化工作流编排器；
- 要求用户维护分类、归档、标签和复杂项目看板；
- 把所有 Goal、PACE 或自主行为暴露成企业任务；
- 为展示“智能”而暴露原始思维链；
- 在没有真实场景前批量接入 ERP、CRM 等系统；
- 在向量服务缺失时提供能力残缺却显示正常的降级模式。

## 14. 下一步

在进入代码实现前，围绕阶段 A 单独完成《本地企业资料库 V1》技术设计，重点确认：

- 资料源、文档、解析结果、向量索引和授权的数据模型；
- 现有附件解析、记忆向量库和动态工具索引的复用边界；
- 文件监听、增量索引、删除和重建策略；
- Agent 工具、Gateway RPC 与 Desktop 页面边界；
- Person 权限与本地宿主机权限的关系；
- Windows、macOS、Linux 路径和文件系统差异；
- 历史 Agent 数据库的增量升级方案；
- 向量服务启动依赖和异常恢复语义。
